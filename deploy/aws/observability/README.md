# Benchmark observability (Grafana Cloud)

Alloy on each EC2 host scrapes local metrics and ships journald logs; CloudWatch
metrics for DynamoDB and S3 are pulled by Alloy on the broker host. Everything
lands in Grafana Cloud (Prometheus + Loki) with an external label `run_id`.

OS choice: Amazon Linux 2023 (dnf, preinstalled AWS CLI, systemd). Alloy is
pinned (`ALLOY_VERSION`, default 1.10.1) and installed from the Grafana rpm repo.

## Layout
- `alloy/config.alloy` common: remote_write, node exporter (`prometheus.exporter.unix`), journald to Loki.
- `alloy/broker.alloy` scrapes manibroker `:9100`, manicp `:9101`, and CloudWatch.
- `alloy/loadgen.alloy` scrapes the load generator (`LOADGEN_METRICS_ADDR`, default `127.0.0.1:9102`; optional).
- `alloy/alloy.service`, `install-alloy.sh` (idempotent, for user-data), `iam-cloudwatch-read.json`.
- `dashboards/*.json` (overview, pipeline, aws, hosts), generated by `gen/gen_dashboards.py`; edit the generator, not the JSON.
- `apply-dashboards.sh`.

Alloy loads the directory `/etc/alloy/` (config.alloy + exactly one role file).
Validated with `docker run grafana/alloy:v1.10.1 validate <dir>` for both roles.

## Secrets (SSM Parameter Store, never committed)
Under `/manifester/<run>/` (SecureString for the key):

| name | content |
|---|---|
| `grafana/prom_url` | `https://prometheus-prod-XX-....grafana.net/api/prom/push` |
| `grafana/prom_user` | Prometheus instance id (number) |
| `grafana/loki_url` | `https://logs-prod-XXX.grafana.net/loki/api/v1/push` |
| `grafana/loki_user` | Loki instance id (number) |
| `grafana/api_key` | Cloud access policy token with `metrics:write`, `logs:write` |
| `aws/ddb_table`, `aws/s3_bucket` | broker host only |
| `aws/s3_metrics_filter_id` | optional, default `manifester-bench` |

`install-alloy.sh` reads them with the instance role and writes
`/etc/alloy/alloy.env` (0600). Grafana URL/token for the dashboards script are
separate and stay on your workstation (`GRAFANA_URL`, `GRAFANA_API_TOKEN`:
service account, role Editor).

User-data: `RUN=<run> ROLE=broker|loadgen OBS_DIR=<checkout>/deploy/aws/observability bash $OBS_DIR/install-alloy.sh`.
The instance role needs `iam-cloudwatch-read.json` (broker host; the SSM statement is needed on both hosts, adjust the parameter ARN prefix if the path differs) plus `kms:Decrypt` if a CMK encrypts the SecureStrings.

## CloudWatch: why Alloy's embedded YACE, not a Grafana CloudWatch data source
Alloy's `prometheus.exporter.cloudwatch` is YACE. Chosen because (1) the series
share the Prometheus store and the `run_id` external label with the app metrics,
so one dashboard overlays broker-side and AWS-side latency in one query;
(2) credentials are the instance role, no AWS keys in Grafana Cloud; (3) no
data-source provisioning step. Cost: 1-minute resolution and CloudWatch
`GetMetricData` calls (scraped every 60 s, a few cents per run). Metric names
follow YACE: `aws_dynamodb_successful_request_latency_average`, label
`dimension_Operation`, etc. Verify label spelling on first scrape (Explore:
`{__name__=~"aws_dynamodb.*"}`); if it differs, fix the AWS dashboard variables.

### What Terraform must provide
1. S3 bucket metrics configuration (request metrics are off by default and billed as custom metrics):
   `aws_s3_bucket_metric` with `bucket = <bench bucket>` and `name = "manifester-bench"` and **no filter** (whole bucket), or a prefix filter that covers the segment prefix. The `name` is the CloudWatch `FilterId` dimension and must equal SSM `aws/s3_metrics_filter_id`. Metrics appear about 15 min after enabling; enable it before the run.
2. SSM parameters above, and `aws/ddb_table` / `aws/s3_bucket`.
3. Instance profile policy from `iam-cloudwatch-read.json` on the broker host (cloudwatch:GetMetricData/GetMetricStatistics/ListMetrics, tag:GetResources, ssm read).
4. DynamoDB needs nothing extra (table metrics are on by default). The static discovery covers operations TransactWriteItems, BatchGetItem, GetItem, Query; add a block in `broker.alloy` for others.

## Dashboards
`./apply-dashboards.sh --dry-run` then `GRAFANA_URL=... GRAFANA_API_TOKEN=... ./apply-dashboards.sh` (optional `GRAFANA_FOLDER_UID`). Idempotent (overwrite by uid). Variables: `ds_prom`, `ds_loki` (pick your Cloud data sources), `run_id`, `host` (Hosts). Overview has a Loki panel `{run_id="$run_id", level=~"warn|error|..."}`. Dashboards show annotations tagged `manifester` + `run:<run_id>`.

Caveats: "ack latency" is seal to commit answer inside the broker; it excludes time batches wait in the open segment (panel "segment open age"); client-side produce latency comes from the load generator. Logs are labelled `level` from the JSON `level` field or logfmt `level=` (lower-cased); other fields (run_id in the body, broker_id) are queryable with `| json`.

## Annotating a run
```
now=$(($(date +%s)*1000))
curl -sS -X POST "$GRAFANA_URL/api/annotations" -H "Authorization: Bearer $GRAFANA_API_TOKEN" \
  -H 'Content-Type: application/json' \
  -d "{\"time\":$now,\"tags\":[\"manifester\",\"run:$RUN\",\"start\"],\"text\":\"run $RUN start: <workload params>\"}"
# at the end: same with tag "end"; or a region: add "timeEnd":<ms>
```
Use the same call with `"dashboardUID":"mani-overview"` to pin to one dashboard (omit for org-wide).

## Querying after the event
Data is kept in Grafana Cloud (free tier: 14 days metrics/logs; export what you need). Set the time range to the annotation window and choose `run_id`. For ad hoc analysis:
```
curl -sG -u "$PROM_USER:$API_KEY" "$PROM_QUERY_URL/api/v1/query_range" \
  --data-urlencode 'query=histogram_quantile(0.99, sum by (le) (rate(manibroker_segment_seal_to_ack_seconds_bucket{run_id="RUN"}[1m])))' \
  --data-urlencode start=... --data-urlencode end=... --data-urlencode step=15
logcli query --org-id=$LOKI_USER '{run_id="RUN", level=~"warn|error"}' --since=2h
```
(`PROM_QUERY_URL` is the Cloud `.../api/prom` base; the read key needs `metrics:read`, `logs:read`.)
Also check `up{run_id="RUN"}` first: a gap in `up` means Alloy lost the host, not that the broker idled.
