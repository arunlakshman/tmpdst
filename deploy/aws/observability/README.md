# Benchmark observability (Grafana Cloud)

Alloy on each EC2 host scrapes local metrics and ships journald logs; CloudWatch
metrics for DynamoDB are pulled by Alloy on the control-plane host and S3 by Alloy on the broker hosts. Everything
lands in Grafana Cloud (Prometheus + Loki) with an external label `run_id`.

OS choice: Amazon Linux 2023 (dnf, preinstalled AWS CLI, systemd). Alloy is
pinned (`ALLOY_VERSION`, default 1.10.1) and installed from the Grafana rpm repo.

## Layout
- `alloy/config.alloy` common: remote_write, node exporter (`prometheus.exporter.unix`), journald to Loki.
- `alloy/broker.alloy` scrapes mdsbroker `:9100` and CloudWatch S3 request metrics.
- `alloy/cp.alloy` (the single control-plane host, role label `cp`) scrapes mdscontrolplane `:9101` and CloudWatch DynamoDB metrics.
- `alloy/loadgen.alloy` scrapes the WarpStream `benchmark-producer` Prometheus port (`127.0.0.1:8081`, up only while a cell runs). `kafka-producer-perf-test` exposes no metrics; the harness keeps its stdout summary.
- `alloy/alloy.service`, `install-alloy.sh` (idempotent, for user-data), `iam-cloudwatch-read.json`.
- `dashboards/*.json` (overview, pipeline, aws, hosts), generated by `gen/gen_dashboards.py`; edit the generator, not the JSON.
- `apply-dashboards.sh`.

Alloy loads the directory `/etc/alloy/` (config.alloy + exactly one role file).
Validated with `docker run grafana/alloy:v1.10.1 validate <dir>` for all three roles.

## Secrets (SSM Parameter Store, never committed)
Under `/mds-bench/` (the Terraform `allowed_ssm_param_prefix`; SecureString for the key and token). Names are the Terraform variable defaults:

| name | content |
|---|---|
| `grafana/remote_write_url` | `https://prometheus-prod-XX-....grafana.net/api/prom/push` |
| `grafana/user` | Prometheus instance id (number) |
| `grafana/loki_url` | `https://logs-prod-XXX.grafana.net/loki/api/v1/push` |
| `grafana/loki_user` | Loki instance id (number) |
| `grafana/prom_api_key` | SecureString, access policy token with `metrics:write` |
| `grafana/loki_api_key` | SecureString, access policy token with `logs:write` |
| `grafana/api_key` | optional SecureString: one combined token (`metrics:write` + `logs:write`), used for whichever of the two above is missing |
| `grafana/url`, `grafana/annotation_token` | optional, read by the benchmark harness only: stack URL (`https://ORG.grafana.net`) and a service-account token (Editor) for run annotations |
| `aws/ddb_table`, `aws/s3_bucket`, `aws/s3_metrics_filter_id` | broker host only; Terraform passes them as environment variables, so these params are only needed when running the installer by hand (filter default `mds-bench`) |

`install-alloy.sh` reads them with the instance role and writes
`/etc/alloy/alloy.env` (0600). Grafana URL/token for the dashboards script are
separate and stay on your workstation (`GRAFANA_URL`, `GRAFANA_API_TOKEN`:
service account, role Editor).

Terraform user-data syncs this directory to the host (`artifacts/observability/`) and runs `RUN=<run> ROLE=broker|loadgen OBS_DIR=... bash install-alloy.sh`; it also accepts `SSM_PREFIX` and `PARAM_*` overrides. The file `/etc/alloy/alloy.env` holds `RUN_ID HOST_ROLE HOST_NAME AWS_REGION GRAFANA_PROM_URL GRAFANA_PROM_USER GRAFANA_LOKI_URL GRAFANA_LOKI_USER GRAFANA_PROM_API_KEY GRAFANA_LOKI_API_KEY` (+ `BROKER_ID DDB_TABLE S3_BUCKET S3_METRICS_FILTER_ID` on the broker; `BROKER_ID` (1..N, from `/etc/mds/host.env`) becomes the `broker` label on every mdsbroker/mdscontrolplane series, which the dashboards' `$broker` variable and the per-broker/skew panels use). Host metrics come from Alloy's embedded `prometheus.exporter.unix`; there is no separate node_exporter.
The instance role needs `iam-cloudwatch-read.json` (broker host; Terraform attaches it; the SSM statement covers `/mds-bench/*`) plus `kms:Decrypt` if a CMK encrypts the SecureStrings.

## CloudWatch: why Alloy's embedded YACE, not a Grafana CloudWatch data source
Alloy's `prometheus.exporter.cloudwatch` is YACE. Chosen because (1) the series
share the Prometheus store and the `run_id` external label with the app metrics,
so one dashboard overlays broker-side and AWS-side latency in one query;
(2) credentials are the instance role, no AWS keys in Grafana Cloud; (3) no
data-source provisioning step. Cost: 1-minute resolution and CloudWatch
`GetMetricData` calls (scraped every 60 s, a few cents per run). Metric names
follow YACE: `aws_dynamodb_successful_request_latency_average`, label
`dimension_Operation`, etc. These `aws_*` names and labels are derived from YACE conventions and have not been seen live; verify on first scrape (Explore:
`{__name__=~"aws_dynamodb.*"}`); if it differs, fix the AWS dashboard variables.

### What Terraform must provide
1. S3 bucket metrics configuration (request metrics are off by default and billed as custom metrics):
   `aws_s3_bucket_metric` with `bucket = <bench bucket>` and `name = var.s3_metrics_filter_id` (default `mds-bench`) and **no filter** (whole bucket). The `name` is the CloudWatch `FilterId` dimension; Terraform passes the same value to Alloy as `S3_METRICS_FILTER_ID`, so they cannot drift. Metrics appear about 15 min after enabling; enable it before the run.
2. The `grafana/*` SSM parameters above (created by the operator).
3. Instance profile policy from `iam-cloudwatch-read.json` on the broker host (cloudwatch:GetMetricData/GetMetricStatistics/ListMetrics, tag:GetResources, ssm read).
4. DynamoDB needs nothing extra (table metrics are on by default). The static discovery covers operations PutItem, GetItem, Query, BatchWriteItem; add a block in `cp.alloy` for others.

## Dashboards
`./apply-dashboards.sh --dry-run` then `GRAFANA_URL=... GRAFANA_API_TOKEN=... ./apply-dashboards.sh` (optional `GRAFANA_FOLDER_UID`). Idempotent (overwrite by uid). Variables: `ds_prom`, `ds_loki` (pick your Cloud data sources), `run_id`, `host` (Hosts). Overview has a Loki panel `{run_id="$run_id", level=~"warn|error|..."}`. Dashboards show annotations tagged `mds` + `run:<run_id>`.

Caveats: "ack latency" is seal to commit answer inside the broker; it excludes time batches wait in the open segment (panel "segment open age"); client-side produce latency comes from the load generator. Logs are labelled `level` from the JSON `level` field or logfmt `level=` (lower-cased); other fields (run_id in the body, broker_id) are queryable with `| json`.

## Annotating a run
```
now=$(($(date +%s)*1000))
curl -sS -X POST "$GRAFANA_URL/api/annotations" -H "Authorization: Bearer $GRAFANA_API_TOKEN" \
  -H 'Content-Type: application/json' \
  -d "{\"time\":$now,\"tags\":[\"mds\",\"run:$RUN\",\"start\"],\"text\":\"run $RUN start: <workload params>\"}"
# at the end: same with tag "end"; or a region: add "timeEnd":<ms>
```
Use the same call with `"dashboardUID":"mds-overview"` to pin to one dashboard (omit for org-wide).

## Querying after the event
Data is kept in Grafana Cloud (free tier: 14 days metrics/logs; export what you need). Set the time range to the annotation window and choose `run_id`. For ad hoc analysis:
```
curl -sG -u "$PROM_USER:$API_KEY" "$PROM_QUERY_URL/api/v1/query_range" \
  --data-urlencode 'query=histogram_quantile(0.99, sum by (le) (rate(mdsbroker_segment_seal_to_ack_seconds_bucket{run_id="RUN"}[1m])))' \
  --data-urlencode start=... --data-urlencode end=... --data-urlencode step=15
logcli query --org-id=$LOKI_USER '{run_id="RUN", level=~"warn|error"}' --since=2h
```
(`PROM_QUERY_URL` is the Cloud `.../api/prom` base; the read key needs `metrics:read`, `logs:read`.)
Also check `up{run_id="RUN"}` first: a gap in `up` means Alloy lost the host, not that the broker idled.
