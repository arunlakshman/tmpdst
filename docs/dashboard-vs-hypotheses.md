## 3. Other things in the data that do not fit the story

1. **Index lag in the doc is the standby's number** (H6); the real indexer lag is a 10 s sawtooth (mean 9 s, max 13 s), so the conclusion holds, the cited panel does not.
2. **Checkpoint size grows with the run**: `manicp_log_checkpoint_bytes` 0.74 MB (smoke), 1.1 MB (500k), 30 MB (750k), 75 MB (1M), 115 MB (kill stage), 156 MB on the restarted/standby node; CP RSS follows (143 MB, 367 MB, 528 MB, 751 MB). Checkpoint age on the active node reaches 170 s. A 5-minute-checkpoint, in-memory-built checkpoint that scales with window content (log-cp-service.md "checkpoints built in memory") is a limit candidate for longer runs; the doc's "RSS 497 MiB" is a 1M number only.
3. **S3 histogram sensitivity**: all stage p99 values 0.254-0.255 (S3) and 0.317-0.319 (segment) are bucket edges. The doc's "p99 318 ms" and "255 ms" are not measurements of the tail.
4. CP `UpdateItem` ConditionalCheckFailed 0.05-0.08/s is steady, including at idle (H2).
5. The doc's smoke row is stronger than a 35 s interior window shows (my 13.9 slots/s vs doc 24.2): smoke is mostly ramp, so use only the three load stages for rates.

## 4. H10: why the CloudWatch S3 metrics read 0

Evidence from the series themselves:
- Series exist with labels `dimension_BucketName=manifester-bench-w4-478483354994`, `dimension_FilterId=manifester-bench`, `name=s3_requests`; `up{job="cloudwatch"}` = 1 (no scrape error, so IAM and region are fine).
- Each `aws_s3_*` series has one sample, value 0, timestamp 23:42:44Z (before any load), and nothing newer. With `honor_timestamps = true` and YACE's default (`nil_to_zero` true in Alloy), "CloudWatch returned no datapoints" is exported as 0. The DynamoDB static jobs, same exporter, return data (`ConsumedWriteCapacityUnits` tracks the load; latency per op 1-5 ms), so the exporter works.
- The FilterId in Terraform (`aws_s3_bucket_metric.all`, `name = var.s3_metrics_filter_id` = `manifester-bench`) matches the Alloy dimension, so a name mismatch is not the cause. w2 shows the same (0 for the full run).

So CloudWatch has no S3 request-metric datapoints in the window the exporter asks for. Candidates, to check in this order (not verifiable now, the stack is gone):
1. The exporter asks only for the last `period` (1 m, no `delay`/`length`), while S3 request metrics are published late (several minutes, and only for minutes with requests after the configuration exists; AWS says up to 15 min after enabling). Fix in `broker.alloy` metric blocks: add `length = "10m"`, `delay = "5m"` (or `add_cloudwatch_timestamp = true`) and set `nil_to_zero = false` so a missing datapoint is a gap, not a fake 0.
2. The bucket metrics configuration is not active: check during a run with `aws s3api get-bucket-metrics-configuration --bucket <b> --id manifester-bench` and `aws cloudwatch list-metrics --namespace AWS/S3 --dimensions Name=BucketName,Value=<b> Name=FilterId,Value=manifester-bench --region ap-south-2`. Empty `list-metrics` after 15+ min of traffic means the request metrics are not being emitted (then the Terraform resource, not Alloy, is the problem; the resource is in `ops/deploy/aws/terraform/storage.tf` line 43 and is created with the bucket, so it exists for the whole run).
3. Only the Alloy S3 job pins all four dimensions; a wrong dimension set returns nothing and still prints 0 (not the case here: labels match).

What is needed: request metrics enabled on the bucket (present in Terraform), the exporter window widened as in (1), `nil_to_zero=false`, and 15 min of lead time before the first stage. The broker-side numbers (`manibroker_s3_*`: PUT/s from `attempt_seconds_count`, errors, retries, bytes from `s3_request_bytes`) already give S3 request rate, size and latency, so aws 2, 3 (CW rows) and 4 can be dropped without losing information, except server-side time-to-first-byte.
